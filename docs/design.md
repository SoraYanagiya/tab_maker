# ギターTAB譜自動生成システム 設計書

## 1. 目的

五線譜で表現された単音旋律を入力し、ギター向けのTAB譜を自動生成する。

目標は以下の通り。

- 五線譜からギターの演奏可能な指使いを選定してTAB譜に変換する
- ポジションの移動をできるだけ少なくする
- 一つの弦で使える指が4本までという制約を考慮する
- 最初は単音弾きに対応し、将来のバッキング対応を前提とする
- 生成結果は「演奏しやすさ」を優先し、機械的な最短フレット検索ではなく実践的な指使いを選ぶ

---

## 2. 背景と課題

ギターTAB譜は、単に音程を変換するだけではなく、指板上での実際の運指を考慮した指使いが重要になる。

特に以下の制約がある。

- ギターは通常EADGBEの標準チューニングで、同じ音は複数の弦・フレットで出せる
- 近い音を連続して弾くとき、ポジションを遠く移動させると演奏が難しくなる
- 1弦で使える指が4本までであるため、同時に複数音を持つ場合はその制約が必要
- 単音弾きでは「音の正しさ」だけではなく「運指の自然さ」が重要になる

よって、TAB生成はただのマッピング問題ではなく、最適化問題として扱うのが妥当である。

---

## 3. 対象範囲

### 3.1 v1 の対象

- 単音旋律の入力
- 1音ずつ順に演奏するパターン
- 標準チューニングの6弦ギターを前提
- 音価や休符の保持
- 単純なメロディに対するTAB出力
- 五線譜編集における基本的な記譜要素（臨時記号・付点・タイ・調号・拍子記号など）への対応
- プロジェクト単位でのデータ保存・再読み込み

### 3.2 v2 の対象（実装済み）

- 和音（複数音の同時演奏）の入力・最適化・表示
- 指板上での重なりや和音の選定、セーハの判定
- 連続する和音に対する運指最適化

### 3.3 v3 以降の対象

- バッキング特有の表現（ストローク、アルペジオ、ミュート記号）

- 高度な奏法（チョーキング、ハンマリング、スライドなど）

## 4. 要件定義

### 4.1 機能要件

1. 五線譜を入力として受け取り、音符情報を抽出する
2. 音符をギターの各弦・各フレットにマッピングする
3. 運指候補を生成する
4. 直前の演奏位置と比較して、ポジション移動を最小化する
5. 一つの弦に対して使う指の数を4本以下に制限する
6. 生成したTAB譜をテキスト出力する
7. 将来的に、メロディ以外にも和音・バッキングを対応可能にする設計を採用する
8. 五線譜編集では、臨時記号・付点・タイ・調号・拍子記号など基本的な記譜操作に対応する
9. 楽曲データ（音符列・設定・生成結果）をプロジェクト単位で保存し、後から呼び出して編集を再開できる

### 4.2 非機能要件

- 計算が高速で、数十〜数百の音符に対して数秒以内にTABを返す
- 実際のギター奏法に近い指使いを出力する
- 実演で自然に弾ける指板配置を優先する
- 変換ロジックが説明可能で、スコア計算の根拠を持つ

---

## 5. 入出力仕様

### 5.1 入力

初期バージョンでは以下の入力形式を想定する。

- MusicXML
- MIDI
- 画像による五線譜（OCRまたは簡易解析）
- もしくは、テキスト表現の音符列

最低限、v1では以下の情報が必要。

- 音名（C, D, E など）
- オクターブ
- 音価（四分音符、八分音符など）
- 休符の位置
- 連続する音の順序
- 臨時記号（♯・♭・♮）
- 付点の有無
- タイの接続情報
- 調号・拍子記号（小節単位のメタ情報として）

### 5.1.1 記譜オクターブ

ギター譜は慣例として実音より1オクターブ高く記譜する（ト音記号 8vb）。本システムでも五線譜はギター記譜として扱い、TAB譜は実音を表す。

- 五線譜入力・MusicXML: 記譜音高として扱い、変換時に1オクターブ下げて実音にする
- MIDI: 実音のため、読み込み時に1オクターブ上げて五線譜に配置する
- 設定 `notationOctaveShift` で「実音どおり（0）」に切り替えられる

### 5.2 出力

- 6本線のTAB譜テキスト
- 例：

```text
e|----------------------------------
B|----------------------------------
G|----------------------------------
D|--------5-------------------------
A|-----7----------------------------
E|----------------------------------
```

- 可能なら、各音に対して指番号・ポジション・手の移動量を併記
- 将来的には、SVGレンダリングやHTMLプレビューを提供する

## 7. 設計方針

### 7.1 基本思想

TAB生成は以下の順で行う。

1. 音符をギター音程に変換する
2. 可能な弦・フレット候補をすべて列挙する
3. 各候補にスコアを割り当てる
4. 連続する音の間で最良の移動を選択する
5. 生成結果に対して実演しやすさの再評価を行う

### 7.2 スコアリングの原則

各候補には、以下を重みで評価する。

- 同じ弦を続けるときの減点
- フレット位置が近い方を好む
- 位置移動（ポジション変更）の減点
- 1〜4本指で弾けるようにする
- 可能なら開放弦、または近い指板位置を優先する
- 連続した音で、手の同じエリアを維持する
- 開放弦（フレット0）はどのポジションからでも制約なく弾けるため、ポジション移動・手の移動に関するペナルティの対象外とする

例えば、重みは概念的に次のようになる。

```text
score =
  + baseFretPreference
  + stringPreference
  + positionStability
  - handShiftPenalty
  - wideJumpPenalty
  - fingerConflictPenalty
  - barrePenalty
```

### 7.3 ポジションの考え方

「ポジション」とは、ギターで手の位置をどこに置くかの概念である。

- 例：3フレットポジション、5フレットポジションなど
- 同じポジションを維持できれば、手の移動が少なくて済む
- ただし、音域が必要なポジションから外れる場合には、別のポジションに移動する

TAB生成では、単に最も近いフレットを選ぶのではなく、連続した音列に対して「ポジション帯を維持する」ことを優先する。

### 7.4 開放弦の扱い

開放弦（フレット0）は左手でどこも押さえずに鳴らせるため、手のポジションに一切依存しない。したがって以下のルールを設ける。

- 開放弦を弾く音は、どのポジションに属しているとも見なさない（ポジション未確定として扱う）
- 直前・直後の音が開放弦の場合、ポジション移動とはみなさず、手の移動コストを課さない
- 開放弦を挟んで前後にフレット音がある場合、ポジションは開放弦をまたいで直前のフレット音のポジションを維持しているものとして評価する
- これにより、開放弦を活用した運指（同一ポジション内に留まるための開放弦利用）が自然に高スコアとなる

## 8. アルゴリズム設計

### 8.1 基本フロー

```text
入力五線譜
  -> 音符抽出
  -> MIDI変換
  -> 可能弦・フレット候補生成
  -> 候補スコア計算
  -> 動的計画法(DP)またはビームサーチで最適経路選定
  -> TAB譜レンダリング
  -> 出力
```

### 8.2 候補生成

各音に対して、次の弦・フレット候補を一覧化する。

- 6弦〜1弦すべてを候補にする
- 各弦で、対象音に一致するフレットを調べる
- 一致しない場合でも、音の近いフレットを候補化する（ただし演奏可能か、指板上の実用性を見て重みを変える）
- 開放弦は優先度を高める

候補数は限定して、音に対して必要以上の候補を増やしすぎないことが重要。

### 8.3 遷移コスト

n 音目の候補を選ぶとき、n-1 音目の選択との間で以下を評価する。

- 同じ弦ならコストを低くする
- 近いフレットならコストを低くする
- 別ポジションへの移動は高コスト
- 大きく手を動かす場合は大きなペナルティ
- 1弦で4指を超えないように調整

概念的な遷移コストは次のようになる。

```text
transitionCost =
  1 * fretDistance
  + 15 * positionChange
  + 2 * stringChange
  + 12 * largeHandMove
  + fingerConstraintPenalty
```

ここで重みは調整可能で、実演のしやすさに応じてチューニングする。上記は実装時のチューニング結果であり、「ポジション内での弦移動は安く、手のポジション移動は高く」という配分になっている。これにより、音列が同一ポジションに収まる限り手を動かさない運指が選ばれる。

`positionChange` の重みは、曲全体を通したポジション移動を最小化する目的で6から15に引き上げた。探索自体は各時点までの累積コストが最小となる状態だけを残す動的計画法であり（ビーム幅は状態数に対して十分大きく、実質的に厳密解になっている）、この重みを上げることで「多少ぎこちない指使いや弦選択になってもポジションを維持する」方向に最適解が変わる。ランダムに生成した60曲の旋律で検証したところ、6→15への変更で移動回数が平均202→160回（約21%減）に減少し、15を超えると改善が鈍化した。

各項の意味は次のとおり。

- `fretDistance`: 同一弦上でのフレット移動量
- `positionChange`: 手のポジション（人差し指の位置）が動いたフレット数
- `stringChange`: 弦をまたいだ場合に1
- `largeHandMove`: ポジション移動が5フレット以上の場合に1
- `fingerConstraintPenalty`: 同じ指で別のフレットを連続して押さえる場合などのペナルティ

### 8.3.1 時間的制約（手の移動速度）

人間の手は、短い時間ではおおよそ5フレット以内しか移動できない。したがって、遷移コストは音符間の時間（拍数）も考慮する。

- 音価が短いほど、許容されるポジション移動量は小さくなる
- 許容量の目安は次のとおり

```text
allowedShift(beats) = 5 * max(1.0, beats / 1.0拍)
```

- 16分音符〜4分音符の間隔: 5フレットまで
- 2分音符の間隔: 10フレットまで
- 全音符の間隔: 20フレットまで

許容量を超える移動には大きなペナルティ（超過1フレットあたり40）を課し、他に選択肢がある場合は必ず回避させる。回避できない場合は、演奏上の無理がある箇所として警告（`shift_too_fast`）を出す。

なお、直前の音が開放弦であればその音価の分だけ手を動かす時間が稼げる。開放弦はそもそも手の位置に依存しないため（第7.4節）、「開放弦を鳴らしている間にポジション移動する」という実際の演奏テクニックが自然に選ばれる。

### 8.3.2 開放弦による補正

前後どちらかの候補が開放弦（fret == 0）である場合は、第7.4節の方針に基づき次のように補正する。

- `fretDistance` は開放弦側を0として扱う（フレット移動が発生しないため）
- `positionChange` と `largeHandMove` は0とする（開放弦は手の位置に依存しないため）
- ポジション帯は、開放弦を無視して直前のフレット音のポジションを引き継ぐ
- `stringChange` は通常どおり評価する（弦をまたぐ動作自体は発生するため）

### 8.4 最適化手法

v1では次のいずれかを採用する。

- 動的計画法(DP)
- ビームサーチ

最小の計算コストで実用的な結果を出すには、ビームサーチが柔軟である。以下を状態として持つのが有効。

- 最後に弾いた弦
- フレット
- ポジション帯
- 直前の指使い
- 指の使用状態

この状態数が増えると計算量が増えるので、v1では必要最小限の状態に絞る。

## 9. 4指制約と和音

### 9.1 単音での扱い

- 単音弾きでは一つの弦に対し最大1音のみを考える
- 指は1音につき1本で、ポジション内（人差し指から小指までの4フレット）に収まることを候補生成の条件とする

### 9.2 和音の扱い（実装済み）

同時に鳴る音は「イベント」としてまとめ、単音も和音も同じ探索経路で扱う。

**候補生成**

1. 各音について、鳴らせる弦とフレットを列挙する
2. 和音のポジションを「押さえる中で最も低いフレット」と定義し、そのポジションから4フレット以内（＋開放弦）に収まる組み合わせだけを残す
3. 各音を**別々の弦**に割り当てる（同一弦に2音は置けない）

**指の割り当て**

- 低いフレットから、低い弦の側から順に指を当てる。これは実際の運指と一致する（例: Eメジャーは 3弦1f=人差し指、5弦2f=中指、4弦2f=薬指）
- 同じフレットでも別々の指を使える（4本に収まる限りセーハにはしない）
- 押さえる音が5つ以上で指が足りない場合のみ、最低フレットを人差し指1本でまとめるセーハを使う
- セーハが押さえてしまう弦を開放弦として鳴らす形は除外する

**和音固有のコスト（設計書 7.2 の barrePenalty を含む）**

```text
chordCost =
  Σ(各音の候補コスト)
  + 2 * フレット幅（最高フレット − 最低フレット）
  + 5 * セーハ（人差し指以外のセーハはさらに +10）
  + 2 * 鳴らす弦に挟まれた鳴らさない弦の数（ミュートが必要）
  + 6 * 弦をまたぐ配置（低い弦に高い音がある）
```

**遷移コスト**

単音と同じ式（第8.3節）を使う。前後の比較には和音の最低フレットとポジションを用い、開放弦のみの和音は手の位置に依存しないものとして扱う（第7.4節）。

**検証**

標準的なコード（C・G・Am・D・E・F・Bm）について、生成される押さえ方が教科書どおりの運指と一致することをテストで確認している。Fのように6音を押さえる形では、セーハが選ばれ警告として通知される。

## 10. 例外と制約

- 極端に高い音域では、ポジション境界を超える可能性がある
- 同音異名（例えば C# と Db）を同一視する必要がある
- 和音を持つ入力では、単音アルゴリズムでは不自然な結果が出るため、v1では対象外とする
- 連続で大きく上下に動くメロディは、ポジション移動を避けると「弾きにくい」TABになることがある。そのため、手の移動と音域のバランスを総合的に考慮する

## 11. システムアーキテクチャ

```text
Presentation Layer
  - UI/入力フォーム
```

- レンダラーが、最終的なTAB譜を文字列・SVG・HTMLで出力する
- プロジェクトリポジトリが、Note列・設定・生成結果をプロジェクト単位で永続化する（第17.7節）

## 13. テスト戦略

### 13.1 単体テスト

- 音符抽出が正しいか
- 弦・フレット候補生成が妥当か
- スコア計算が意図どおりか
- 連続音に対する移動コストが生じているか

### 13.2 統合テスト

- 既知のメロディが安定してTAB譜に変換されるか
- 無理なポジション移動を避けているか
- 複数の候補の中から自然な運指が選ばれるか

### 13.3 代表的なテストケース

- スケール音列
- 連続した上行・下行メロディ
- 開放弦を含むメロディ
- 大きな音程ジャンプがある曲線
- 複数オクターブにまたがる旋律

## 14. 将来拡張計画

### 14.1 バッキング対応

次段階では、メロディだけでなく、以下を扱えるようにする。

- 伴奏コード
- 複数音の同時発音
- フレーズごとの和音構成
- 低音・中音・高音の役割分担

このとき、指使い最適化は単音列ではなく「複数ノートの同時配置」を考慮する必要がある。

### 14.2 運指の人間味

- 「親指は使わない」前提
- 「人差し指〜小指を活用する」運指の自然さ
- 連続アーティキュレーションに対する指の引き継ぎ
- 左手の負担感をスコアに反映

### 14.3 UI 拡張

- 五線譜のプレビュー
- TAB譜生成結果の比較表示
- 指番号の可視化
- ポジションの可視化
- 「自然さ」や「簡単さ」の重み調整

---

## 15. リスクと懸念

### 15.1 変換精度のバランス

音の正しさと運指の自然さはトレードオフになる。

- ただし「最短フレット」を選ぶと実演しづらいことが多い
- そのため、スコアリングに「人間の運指」を反映する必要がある

### 15.2 5線譜入力のバリエーション

入力形式が MusicXML 以外になると、ノート抽出の処理が複雑化する。

- v1では主要入力形式に絞る
- 画像入力は将来に回すのが安全

### 15.3 バッキングへの拡張

和音・コードの最適化は、単音最適化と設計が大きく異なる。

- v1を単音版として分離し、v2でバッキング版を別設計とするのが妥当

---

## 16. 推奨アーキテクチャ判断

短期的には、最適化対象を単音メロディに限定し、機械的にではなく「運指を重視した探索」を採用するのが適切である。

理由は以下の通り。

- 目標が明確で、実作業として取り組みやすい
- 単音の変換は評価しやすく、テストがしやすい
- 後から和音・バッキング対応を追加しやすい
- 実際のギタリストが「使いやすいTAB」を求めるには、運指最適化が不可欠

## 17. GUIアプリケーション設計

### 17.1 方式

GUIはWebアプリケーションとして実装する。

- フロントエンド: ブラウザ上で動作するUI（五線譜入力・TAB譜プレビューを担当）
- バックエンド: 第12章のPython実装をAPIサーバーとして公開し、フロントエンドから呼び出す

フロントエンドとバックエンドを分離することで、五線譜入力UIの実装（音符のクリック配置、ドラッグ編集など）にJS系の記譜ライブラリ（例: VexFlow）を活用しつつ、変換ロジックは既存のPython資産（music21, 最適化エンジン）をそのまま再利用できる。

### 17.2 画面構成

#### 五線譜入力画面

- 目的: ユーザーが五線譜上で音符列を作成・編集する
- 主要要素
  - 五線譜キャンバス（ト音記号、v1では単一パートのみ）
  - 音価選択パレット（全音符・二分音符・四分音符・八分音符・休符 など）
  - 臨時記号（♯・♭・♮）の付与
  - 付点の付与
  - タイ／スラーによる音符の接続
  - 調号・拍子記号の設定
  - 音符のドラッグによる音高変更
  - 音符・小節の選択、コピー／ペースト、削除
  - 小節の追加・削除
  - Undo / Redo
  - MusicXML / MIDI ファイルのインポート（複数パート/トラックを含む場合は、どのパートを読み込むか選択できる）
  - キーボードショートカットによる入力（音価切り替え、臨時記号トグルなど）
  - 鍵盤入力（画面上の仮想ピアノ鍵盤、およびPCキーボードのタイピングピアノ）
  - 「TAB生成」ボタン
- 出力: 入力された音符列を、ドメインモデルNoteに対応するJSON形式でバックエンドに送信する

将来的にはさらに、連符（三連符など）、複数声部、装飾記号（スタッカート・アクセントなど）への対応も検討する（v2以降）。

#### 鍵盤入力

五線譜クリックに加えて、ピアノ鍵盤に見立てた入力方式を提供する。

- 画面上の仮想鍵盤（1オクターブ＋完全4度＝白鍵11・黒鍵7）をクリックして音を入力する
- PCキーボードでも同じ配列を使える（A〜' が白鍵、W・E・T・Y・U・O・P が黒鍵）。Z/Xキーで表示オクターブを上下する
- 弾いた音は、選択中の音符の直後に挿入され、選択がその音に進む（ステップ入力）。これにより連続して弾くだけで音符列を入力できる
- 和音モード（第17.2節）が有効な場合は、選択中の音符に重ねて和音にする
- 黒鍵で入力した音は臨時記号♯として記録する（五線譜クリックによる入力とは異なり、鍵盤入力は常に音高を確定させた状態で渡すため、ツールバーの臨時記号選択より優先する）
- 入力のたびに、その場で短い撥弦音を鳴らして確認できる（再生機能と同じ音源を使用）

#### TAB譜プレビュー画面

- 目的: 生成されたTAB譜を確認する
- 主要要素
  - 6線のTAB表示
  - 指番号・ポジション・手の移動量の重ね表示切り替え
  - 警告（warnings）表示欄（例外的な運指や大きなポジション移動があった箇所）
  - 五線譜側の該当音符とのハイライト同期
  - TABのエクスポート（テキスト / 画像）
- 入力: バックエンドAPIのレスポンス（TAB文字列、および音符ごとの運指詳細）

エクスポートは、閲覧しているウィンドウサイズに影響されない。画像は画面表示とは別に固定幅（1080px・2倍解像度）でレイアウトし直してから書き出すため、どの環境でも同じ小節割り・同じ寸法の画像になる。テキストも同様に、1行あたりの小節数を固定して出力する。

#### 再生

作成した旋律をその場で試聴できるようにする。

- 再生 / 停止（Spaceキー）、テンポ（BPM）指定
- 音符を選択している場合は、その位置から再生する
- 再生位置の音符を、五線譜とTAB譜の両方でハイライトする
- 音源はブラウザ内で合成する（Karplus-Strong方式による撥弦音）ため、音源ファイルや外部通信を必要としない
- 再生音はTAB譜と同じ実音（記譜オクターブ設定を反映した音高）で鳴らす

#### プロジェクト一覧画面

- 目的: 保存済みのプロジェクトを管理し、編集を再開する
- 主要要素
  - プロジェクトカード一覧（プロジェクト名、更新日時、サムネイル）
  - 「新規プロジェクト作成」ボタン
  - プロジェクトの名前変更・複製・削除
  - 検索・並び替え（更新日時順など）
- 出力: 選択したプロジェクトIDで五線譜入力／TABプレビュー画面（分割表示）を開く

### 17.3 画面遷移

1. プロジェクト一覧画面でプロジェクトを新規作成、または既存プロジェクトを開く
2. 五線譜入力画面で音符列を作成・編集する
3. 「TAB生成」を押すとバックエンドAPIを呼び出す
4. 結果をTAB譜プレビュー画面に表示する
5. 必要に応じて入力画面に戻って音符を修正し、再生成する
6. 編集内容はプロジェクトとして保存され、後からプロジェクト一覧画面経由で呼び出せる

v1では左右または上下の分割表示（入力画面とプレビュー画面を同時に表示）を推奨する。編集のたびに再生成結果を確認しながら調整する運用を想定しているため、画面遷移よりも同一ビュー内での往復を優先する。

### 17.4 技術スタック（案）

- フロントエンド: React などのSPAフレームワーク + VexFlow（五線譜レンダリング・入力）
- バックエンド: 既存Python実装をFlaskまたはFastAPIでラップし、`/api/convert` を公開する
- 通信: JSON（音符列 → TAB文字列・運指情報）

### 17.5 API拡張

第12.3節のAPI例を、GUI用途向けに拡張する。

- `inputType` に、五線譜入力画面から生成される音符列JSON形式（例: `"note_list"`）を追加する
- レスポンスに、各音符に対応する指番号・ポジション・移動量（第6.3節 Candidate、第6.4節 State に対応する情報）を含める

#### 17.5.1 パート選択（MusicXML / MIDI インポート）

`POST /api/import` は、MusicXML/MIDIファイルに複数のパート（トラック）が含まれる場合、全パートを抽出してレスポンスに含める。

```text
ImportResponse
- title: string | null
- notes / measures / warnings   // 既定パート（原則、音符を含む先頭のパート）
- parts: ImportPart[]           // 全パート一覧
  - index: int
  - name: string                // トラック名 → 楽器名 → "トラック N" の順で決定
  - noteCount: int
  - notes / measures / warnings // そのパート単独の内容
```

画面側は `parts` が2件以上ある場合、パート名と音符数を一覧表示して選び直せるようにする（第17.2節）。1件しかない場合はそのまま読み込む。

打楽器トラックなど「高さを持たない音」（music21の `Unpitched`）を含むパートは、該当する音符をスキップして警告を出す（クラッシュさせない）。全パートが打楽器のみの場合でも一覧には表示され、既定パートは音符を含むものの中から選ぶ。

### 17.6 状態管理・同期

- 入力画面での編集中は、音符列をフロントエンド側の状態として保持する
- バックエンドへは「TAB生成」操作時にのみ送信し、編集の都度リクエストは行わない
- プレビュー結果は音符インデックスで入力側と対応付け、五線譜⇔TAB間のハイライト同期を可能にする

### 17.7 プロジェクト管理

作成した楽曲データを「プロジェクト」単位で保存し、後から呼び出して編集を再開できるようにする。

#### 17.7.1 プロジェクトモデル

```text
Project
- projectId: string
- name: string
- createdAt: datetime
- updatedAt: datetime
- measures: MeasureInfo[]   // 調号・拍子記号など
- notes: Note[]             // 音符列
- settings: object          // スコアリング重みなど生成時のパラメータ
- generatedTab: object      // 直近のTAB生成結果（キャッシュ、再計算不要にする）
```

#### 17.7.2 保存・読み込み

- 保存はバックエンドAPI経由で行い、ユーザーごとに複数のプロジェクトを保持する
- 編集中は一定間隔、または明示的な「保存」操作でプロジェクトを更新する（自動保存 + 手動保存の併用）
- 「名前を付けて保存」により、既存プロジェクトを複製した新規プロジェクトを作成できる
- ローカルファイルへのエクスポート／インポート（JSON形式）も可能とし、バックアップや共有に利用できるようにする

#### 17.7.3 API拡張

第12.3節のAPIに、プロジェクト管理用のエンドポイントを追加する。

```text
GET    /api/projects            プロジェクト一覧を取得
POST   /api/projects            新規プロジェクトを作成
GET    /api/projects/{id}       プロジェクト詳細を取得
PUT    /api/projects/{id}       プロジェクトを更新（音符列・設定・生成結果を保存）
DELETE /api/projects/{id}       プロジェクトを削除
```

- `PUT /api/projects/{id}` は、五線譜編集画面での自動保存・手動保存の両方から呼び出される
- `generatedTab` を保存しておくことで、プロジェクトを開き直した際に再生成せずに直前の結果をすぐ表示できる

#### 17.7.4 スタンドアロンアプリでの保存先

Webサーバーとして動かす場合はリポジトリ内の `data/projects/` に保存するが、pywebviewによるスタンドアロンアプリ（第17.4節の技術スタックに対する代替実行形態）では、インストール場所やビルドし直しに影響されないよう、OS標準のアプリデータ置き場に保存する。

- macOS: `~/Library/Application Support/GuitarTabMaker/projects/`
- Windows: `%APPDATA%\GuitarTabMaker\projects\`
- Linux: `~/.local/share/GuitarTabMaker/projects/`

ビルドはGitHub Actions（`.github/workflows/build-app.yml`）で自動化し、push のたびに両OS向けアプリを生成する。バージョンタグ（`v*`）を push するとGitHub Releaseにも自動で添付され、利用者はソースをビルドせずダウンロードするだけで使える。

## 18. まとめ

本システムは、五線譜からギターTAB譜へ変換する「運指最適化型の変換器」として設計する。

v1 の核となるのは以下の3点である。

- input: 五線譜の音符列
- process: 弦・フレット候補生成とコスト最適化
- output: 実演しやすいギターTAB譜

特に、ポジションの移動を少なくすることと、1弦あたりの指使用数を4本までに制約することが、実用的なTAB生成の鍵となる。

将来はこの基盤をもとに、和音やバッキングへの拡張を行うことで、より実務的なギター譜面生成システムとして発展させる。
